# DexMani_Policy 仿真评测机制

> 本文描述 DexMani_Policy 的**模型选择、仿真评测 protocol、checkpoint restore、seed/metric/failure contract**。
>
> 历史模型的 constructor semantics（含 prediction type）以所选 checkpoint 的 `resume_contract.agent_config` 与对应源码为准；action/window/normalization 由 checkpoint contract 定义。当前 `config.yaml` 提供环境与评测 protocol；EMA/raw、NFE 是显式 inference 选择。
>
> 系统级训练/评测边界见 [`项目架构.md`](./项目架构.md)。

---

## 1. Evaluation Protocol Overview

DexMani_Policy 将训练、checkpoint selection 和最终性能评测拆成三个阶段：

```text
Training
   │
   ▼
progress milestone checkpoints
   │
   ▼
Checkpoint Selection
   │  paired selection seeds
   │  same inference protocol across candidates
   ▼
best_ckpt.json
   │
   ▼
Final Evaluation
      held-out seeds
```

核心目的有三个：

1. **训练不拥有 best-model 逻辑**：Trainer 只产出 milestone checkpoints。
2. **candidate checkpoint 公平比较**：selection 阶段对候选 checkpoint 使用相同的 paired seed slice。
3. **避免 selection/evaluation leakage**：`best` 的最终评测排除 selection record 已使用的 seeds。

### 1.1 主要入口

```bash
# 一键：selection → held-out eval → demo
bash scripts/eval/eval_pipeline.sh <policy_name> <task_name> <exp_name>

# 分步
bash scripts/eval/select_best_ckpt.sh <policy_name> <task_name> <exp_name>
bash scripts/eval/eval_best_ckpt.sh <policy_name> <task_name> <exp_name>
bash scripts/eval/record_demo.sh <policy_name> <task_name> <exp_name>
```

实验路径和评测环境配置来自实验 config，历史模型语义来自选中的 checkpoint：

```text
experiments/<policy>/<task>/<exp>/
├── config.yaml
├── checkpoints/
├── best_ckpt.json          # selection 完成后生成
├── eval_ckpt_selector/     # selection summary / optional videos
├── eval_dexsim/            # final evaluation outputs
└── demo_videos/            # demo recording outputs
```

`<policy>` 可以包含层级路径（例如 DDP config 的 `policy_name`）；不要根据 config 文件名猜实验目录，优先读取实验保存的 config 与实际目录。

## 2. Checkpoint Selection Protocol

`select_best_ckpt.py` 从实验目录发现 progress milestone checkpoints，然后以固定 protocol 比较候选模型。

### 2.1 Candidate Discovery

milestone checkpoint 的命名中包含 progress percentage；selection 只比较可识别的 milestone candidates，而不是训练过程中的任意临时 checkpoint。

训练侧负责产生候选 checkpoint，selection 侧负责决定哪一个作为 best。两者职责分离。

### 2.2 Phase 1 — Paired Initial Evaluation

```text
candidate checkpoint A ─┐
candidate checkpoint B ─┼─ same selection seed slice
candidate checkpoint C ─┘
```

所有 candidate 使用：

- 相同的 episode positions / selection seeds；
- 相同的 EMA 选择；
- 相同的 denoise steps / NFE；
- 相同的 environment/evaluation config。

因此 checkpoint comparison 的 denominator 一致。

selection budget 由 `cfg.eval.select_best`、dotlist override 和显式 CLI 参数解析，不在本文固定具体 episode 数。

### 2.3 Exact-Tie Batch

Phase 1 后，只有 top candidates 的 success rate 完全相同时才使用下一批 fresh paired seeds 做 tie-break。

如果追加 batch 后仍然 tied，最终 rank key 为：

```text
1. higher success rate
2. lower avg_steps
3. higher global_step
```

`avg_steps` 只在成功 episode 中统计有有效 done-step 的首次物理完成步数，因此它只是 success-rate tie-break，而不是主指标。

### 2.4 Multi-task Selection Metric

selection 内部通过 `collect_episode_details()` 展平 `(task, episode)` units 后累积 `success_list`。因此 multi-task checkpoint ranking 使用的是**episode-level micro success rate**，不是 `MultiTaskSimRunner` 顶层的 macro success rate。

这意味着 selection 与 final `_result.txt` 的主 success-rate 标量语义保持一致：都按实际完成的 `(task, episode)` units 计数。

### 2.5 All-Fail Guard

如果所有 candidate 都得到 0 success，selection 拒绝写出正常的 `best_ckpt.json`。

这避免把“所有模型都失败”静默转换成一个看似合法的 best checkpoint。

### 2.6 `best_ckpt.json`

selection record 是 final evaluation / best-demo 的 handoff contract，保存：

- selected checkpoint identity；
- selection performance summary；
- inference choice（raw/EMA、denoise steps）；
- selection seed record。

读取时使用 strict schema 校验；缺字段、多字段、非法 checkpoint path 或已不存在的 checkpoint 都直接失败。

## 3. Final Held-out Evaluation

`eval_best_ckpt.py` 可以评测：

- selection 得到的 `best`；
- `latest`；
- milestone tag；
- 显式 checkpoint path。

### 3.1 `best` 的特殊语义

当评测 `best` 时：

1. 读取并严格验证 `best_ckpt.json`；
2. 默认复用 selection record 中的 inference choice；
3. 从环境 reference seed pool 中排除 selection 已使用的 seeds；
4. 在剩余 held-out seeds 上做最终评测。

如果 held-out seed 数少于请求 episodes，则使用全部可用 seeds 并记录实际数量；如果没有任何可用 held-out seed，则失败。

### 3.2 Inference Parameter Priority

对于 `best`，EMA/NFE 等 inference 参数的优先级是：

```text
explicit CLI
    > explicit OmegaConf/dotlist override
    > best_ckpt.json inference record
    > experiment config
```

这样既能保证默认复现 selection 的 inference protocol，也允许显式做 NFE/EMA ablation。

非 `best` checkpoint 不依赖 selection record。

### 3.3 Override Boundary

selection/final-eval dotlist 接受 `eval.*`、`env_runner.*`、`training.seed` 等评测控制；显式 EMA/NFE、episodes、video 参数继续生效。`agent` 或 `agent.*` override 在合并前直接报错，包括模型构造中的 `num_inference_steps`；NFE ablation 应使用 `--denoise-steps` 或 `eval.*`。当前 config 的 normalization 不能覆盖 checkpoint normalization。

### 3.4 Demo Handoff

`record_demo.py --ckpt-tag best` 默认也读取 `best_ckpt.json`，复用其中的：

- raw / EMA choice；
- denoise steps。

显式 `--ema` / `--no-ema` 与 `--denoise-steps` 可以覆盖它们。非 `best` demo 使用 `eval.demo` / shared eval config。

Demo 的目的是录制可视化 artifact，不属于 held-out benchmark：默认 seed 选择不会因为 `best` 自动排除 selection seeds；需要复现某个已评测 episode 时应显式传 `--seeds`。

`eval_pipeline.sh --no-videos` 只关闭 final-eval 阶段的视频；pipeline 的 demo 阶段仍然会录制视频。

## 4. Seed and Reproducibility Contract

评测中的“可复现”需要分层理解。

### 4.1 Evaluation Seed Resolution

共享 helper 的基础规则是：

```text
resolved training.seed + fixed offset
```

其中 selection CLI 额外提供 `--seed`，所以 selection 的优先级是：

```text
select_best_ckpt.py --seed
    > resolved training.seed + fixed offset
```

`eval_best_ckpt.py` 当前**没有独立 `--seed` CLI 参数**；final eval 使用 resolved evaluation config 中的 `training.seed + offset`。final-eval dotlist 若显式改写 `training.seed`，也会相应改变 evaluation seed，因为 dotlist 会在 `_setup_eval()` 前合并进 config。

`record_demo.py` 同样没有独立 `--seed`，但可以用 `--seeds` 直接指定要录制的 episode seeds。

### 4.2 Seed Pool Selection

seed pool 在进入 selection/final eval 前会：

1. 保序去重；
2. 使用 evaluation seed 做 deterministic shuffle；
3. 再按 protocol 切 selection / tie-break / held-out slice。

因此**seed selection 本身是确定的**。

### 4.3 Environment RNG

每个 episode 通过：

```python
env.reset(seed=episode_seed)
```

向 simulator 传入 episode seed。

### 4.4 Policy Sampling RNG

`BaseRunner.run_one_episode()` 在每个 episode 开始时重新设置 Torch CPU/CUDA RNG，使生成式 Policy 的初始噪声与 episode seed 绑定。

因此 checkpoint A 与 checkpoint B 在相同 episode seed 上比较时，Policy RNG 从相同 seed 重新初始化。实际噪声还取决于模型的随机数消费顺序、tensor shape 与 inference steps；不同模型或 NFE 不保证逐次抽样完全相同。

### 4.5 Determinism Boundary

以上保证的是：

- seed slice 可重复；
- environment seed 输入可重复；
- policy RNG 初始化可重复。

**不保证不同运行、不同 GPU/driver/kernel 环境下 bitwise-identical trajectory。** 公共训练/评测环境没有承诺开启全局 deterministic CUDA algorithms，因此文档不应声称“重跑永远得到完全相同结果”。

正确表述是：

> Evaluation protocol is seed-reproducible; bitwise hardware determinism is not guaranteed.

## 5. Multi-task Seed Semantics

`MultiTaskSimRunner` 是多个 `TaskTextSimRunner` 的 orchestrator。不同 task 可以拥有不同的 numeric seed pool，因此 multi-task pairing 使用**ordinal position mapping**，而不是强迫所有 task 使用相同数字 seed。

示例：

```text
Task A pool: [101, 203, 307, 411]
Task B pool: [  7,   9,  14,  22]

selected reference positions: [0, 2]

Task A evaluates: [101, 307]
Task B evaluates: [  7,  14]
```

父 runner 以 reference task 的 pool 为选择空间，并将选中的 positions 映射到每个 task 自己的 seed pool。

为了保证所选 position 对所有 task 有效，reference pool 的有效长度受最短 task seed pool 限制。

这意味着 multi-task “paired evaluation” 的单位是**seed position / environment instance position**，不是跨任务共享 numeric seed ID。

## 6. Checkpoint Restore Contract

评测加载 checkpoint 时走统一的严格恢复链：

```text
CheckpointStore.load
      │
      ▼
training checkpoint schema validation
      │
      ▼
checkpoint agent_config + agent action/window/normalization contract
      │
      ▼
validate saved window/normalization and current environment control mode
      │
      ▼
select raw / EMA state
      │
      ▼
instantiate saved constructor; attach saved action/normalization semantics
      │
      ▼
validate_resume_contract(saved agent, build_agent_contract(restored agent))
      │
      ▼
repair torch.compile / DDP prefixes
      │
      ▼
agent.load_state_dict(strict=True)
      │
      ▼
normalizer state validation + saved compact contract validation
```

三个入口 `select_best_ckpt.py`、`eval_best_ckpt.py` 和 `record_demo.py` 共用恢复路径。selection 对每个 candidate（含 tie-break）独立恢复，不能用第一个 candidate 的 constructor 配置替代其他 checkpoint。

当前 config 的 `agent`、顶层模型 window 和 `normalization` 不参与历史 Agent 构造；后续手工修改 `prediction_type` 不会改变旧 checkpoint 的 DDIM 语义。缺失 `agent_config` 不回退当前 config。当前 env runner 的 control mode 仍须与 checkpoint action key 一致。

### 6.1 Agent Compatibility

当前 agent contract 不只描述 parameter shape，还描述 environment-facing action semantics，例如：

- observation/action temporal window（三个字段均为非 bool 正整数，且 `n_obs_steps - 1 + n_action_steps <= horizon`；与训练共用 validator）；
- action dimension / action key；
- control-action dimension；
- Policy-specific hand/TCP dimensions；
- auxiliary-action semantics。

因此：

> 一个 checkpoint 的 tensors 即使能够“看起来匹配”，也不代表它在语义上可以用于当前 Agent。

### 6.2 Raw vs EMA

- `use_ema=True` 时 checkpoint 必须真的包含 EMA state；缺失时直接失败。
- `use_ema=False` 才显式使用 raw model state。

不做 silent fallback。

### 6.3 Prefix Repair

评测会处理训练包装引入的 state-dict prefix，例如：

- `torch.compile` 的 `_orig_mod.`；
- DDP 的 `module.`。

最终始终用 `strict=True` 加载到单卡 inference Agent。

### 6.4 Normalizer Restore

Normalization mode 从 checkpoint 的 `resume_contract.agent.normalization` 严格解析；拟合参数来自选中的 raw/EMA state。校验覆盖字段和 fitted state 的完整性、有限性、非零 scale，当前 config 不得重新定义它们。

DQ-RISE 构造时不读取训练时的 external `codebook_path`；strict state load 恢复 persistent codebook，并验证结构和 hand normalizer 与 Policy 一致。完整 checkpoint 不依赖原 NPZ 文件。

## 7. Observation Runtime

### 7.1 Temporal Ring Buffer

`BaseRunner` 为 configured sensor modalities 维护长度为 `n_obs_steps` 的 temporal buffer。

```text
env.reset / env.step
      │
      ▼
update_obs
      │
      ▼
ring buffer
      │
      ▼
get_stacked_obs
      │
      ▼
(T=n_obs_steps, ...)
      │
      ▼
get_obs_batch
      │
      ▼
(B=1, T=n_obs_steps, ...)
```

冷启动阶段如果有效观测少于 `n_obs_steps`，使用 episode 第一帧在序列头部 padding，使最新真实观测保持在时间窗口尾部。

buffer 满后通过时间索引重新排列为 chronological order。该读取使用 advanced/fancy indexing，不能视为零拷贝接口；优化重点是避免每一步重新分配写入 storage，而不是承诺读取零 allocation。

### 7.2 Modalities

`update_obs()` 只保存 `sensor_modalities` 中声明的字段。

典型语义：

- `joint_state`：进入 temporal buffer，并由 Policy normalizer 处理；
- `point_cloud`：进入 temporal buffer；normalization mode 由 checkpoint contract 定义，非 identity 的 fitted state 随 Agent checkpoint 恢复；
- `rgb`：当 config 将其列入 `sensor_modalities` 时进入 buffer，随后执行与 validation 对齐的确定性 spatial preprocessing；
- `task_text`：通常由 `TaskTextSimRunner` 在 inference boundary 注入，而不是依赖环境 ring buffer。

不要把“RGB”泛化成非传感器模态，也不要把 point-cloud normalization 误写成只由 encoder 内部完成。

### 7.3 RGB Path

Evaluation RGB path 复用 deterministic validation preprocessing：

```text
raw HWC uint8 RGB
    │
    ├── optional resize
    ├── optional center crop (requires resize)
    ▼
CHW uint8/float according to preprocessing path
    │
    ▼
vision encoder / ImageProcessor normalization
```

当前 `BaseRunner.get_obs_batch()` 的 evaluation path 调用 `preprocess_validation_rgb(..., keep_uint8=False)`；training/eval 的 RGB contract 以对应 config 为准，**deployment** 的 RGB contract 以 selected checkpoint 保存的 dataset 语义与 artifact deployment spec 为准（不读当前 config）。

训练时的 random crop / color augmentation 不在 evaluation 中启用。

## 8. Agent Inference and Action Chunk Semantics

公共 inference path：

```text
obs_dict
   │
   ▼
Agent.predict_action
   │
   ├── validate observation contract
   ├── preprocess / normalize
   ├── ObsEncoder → condition
   └── predict_action_from_cond
           │
           ├── generative decoder sampling
           ├── action unnormalize / representation decode
           └── control chunk slicing
```

### 8.1 Default Action Slice

`BaseAgent` 的默认时间对齐规则：

```python
start = n_obs_steps - 1
control_action = pred[:, start : start + n_action_steps]
tail = pred[:, start + n_action_steps :]
```

因此诸如 `pred[:, 1:9]` 只是特定 `(n_obs_steps, n_action_steps)` recipe 的实例，不是架构 contract。

Policy 可以 override `predict_action_from_cond()`；不要假设所有 override 都返回 `tail`。

### 8.2 Model Output vs Control Action

某些 Policy 会预测 auxiliary action dimensions。此时：

```text
model action_dim
    ≠
environment-facing control_action_dim
```

Agent 在 inference boundary 截取真正传入 `env.step()` 的控制维度。

### 8.3 Internal Action Representation

公共 rollout 只要求 Agent 提供可执行的 `control_action`。通常还会返回完整 `pred_action`，但其他诊断字段（例如 `tail`、code index 等）可以是 Policy-specific。

因此 Policy 内部可以使用不同表示，例如 structural/action-dimension tokens 或 reduced/quantized hand representation，只要在 Agent boundary 恢复正确的 environment-facing control semantics。

## 9. Inference Algorithm Families

Evaluation 层通过 Agent 将运行时 `denoise_timesteps` 传给 Action Decoder，覆盖本次推理步数；其采样算法由 decoder/solver 决定。

### 9.1 Diffusion / DDIM

```text
x ~ N(0, I)
   │
   ▼
DDIM timestep schedule
   │
   ├── model(x_t, t, condition)
   └── scheduler.step
   │
   ▼
predicted action sequence
```

model output 的语义由 `prediction_type` 决定，例如 clean sample、noise 或 velocity prediction。

training timesteps 与默认 decoder 构造参数来自 checkpoint；本次 inference steps 由显式 CLI、selection record 与 evaluation config 按已有优先级决定，不在本文固定。

### 9.2 Flow Matching / Euler ODE

典型 rectified path：

```text
x_t = (1 - t) x_noise + t x_data
v*  = x_data - x_noise
```

训练学习 velocity field；推理从 Gaussian noise 出发，通过 ODE integration：

```text
x_{t+dt} = x_t + dt · vθ(x_t, t | condition)
```

Flow Matching 是 training objective；它本身不意味着 one-step inference。

### 9.3 Consistency-enhanced Flow

某些 decoder 会在普通 flow velocity regression 之外加入 teacher/consistency target，并让模型显式接收 target step / step-size conditioning。

当前 [ManiFlow decoder](../dexmani_policy/agents/action_decoders/consistency_flow.py)
用构造参数 `denoise_timesteps` 设置 consistency 训练离散网格，用 `num_inference_steps`
设置默认 Euler 推理 NFE。评测的 `denoise_steps` 通过运行时参数覆盖推理 NFE，
不会修改训练 sampler 或 consistency denominator。不要将构造参数与运行时同名参数混用。

这类模型在 inference 时可能使用训练过的非零 step-size condition。若训练只覆盖 instantaneous-flow condition，而 inference 使用不同 condition，会产生 conditional distribution shift；是否存在这种路径必须从当前 decoder 与 config 验证。

### 9.4 NFE Sweep Fairness

做 NFE sweep 时，不同 NFE 使用同一个 **evaluation reference seed slice**。对于 `best`，该 slice 已排除 selection seeds，因此属于 held-out final-eval seeds；对于 `latest`、milestone 或显式 path，则只是同一评测 seed slice，不应称为 selection-held-out。

这样 success-rate 差异主要反映 inference compute budget，而不是 environment-instance sampling 差异。

## 10. Episode Semantics and Metrics

### 10.1 `success_condition` vs `success`

单 episode 区分两个信号：

```text
success_condition
    = 首次满足任务物理目标的 raw condition

success
    = 环境最终认可的成功结果，可包含 hold / grace 条件
```

`task_done_step` 在首次 truthy `success_condition` 时读取 `env.action_cnt`；如果环境没有提供该 contract，则 done step 可以是 `None`。

因此：

- success rate 使用最终 `success`；
- successful completion speed 使用有值的 `task_done_step`。

### 10.2 Single-task Metrics

```text
success_rate
    = successful episodes / completed valid episodes

avg_steps
    = mean(task_done_step) over successful episodes with a valid done step

avg_steps_all
    = mean(total episode steps) over episode details that have total_steps
```

失败 episode 参与 `success_rate` 和通常的 `avg_steps_all`，但不参与 success-only `avg_steps`。

### 10.3 Multi-task Metrics

Multi-task runner 同时计算：

```text
per-task success rate

macro_success_rate
    = mean(per-task success rate)

micro_success_rate
    = total successful (task, episode) units
      / total completed (task, episode) units
```

macro 衡量 task-level 平均表现；micro 按实际 episode units 加权。两者不应混用。

最终 `eval_best_ckpt.py` 会重新从 episode details 计算 micro statistics：

- `_result.txt` 写入 **micro success rate**；
- `result_details.json` 同时保存 `success_rate`（micro）和 `macro_success_rate`。

因此读取 multi-task 历史结果时，不要把 `_result.txt` 的单值误解为 macro average。

## 11. Failure Semantics

评测严格区分“模型正常执行但任务失败”和“评测系统本身出错”。

### 11.1 Genuine Task Failure

```text
episode executes normally
+ info["success"] == False
→ valid result: success=False
```

这是正常 benchmark outcome。

### 11.2 Fatal Episode Failure

model forward、environment step、OOM、runtime contract 等异常在单任务 runner 中被分类并转换为 `EvalEpisodeError`，随后终止当前评测，而不是记成普通 0% episode 继续。

这避免 infrastructure/model errors 被统计成 task failure。

### 11.3 Multi-task Failure

`MultiTaskSimRunner` 对 child `EvalEpisodeError` 直接向上抛出。某些发生在 task orchestration boundary 的普通 runtime/config errors 可以先记录为 failed task，但最终会拒绝报告 reduced aggregate result，并以异常结束。

因此不能把“缺失一个 task 后剩余任务的 macro average”当成有效 benchmark。

### 11.4 Video Failures

视频是 best-effort artifact：

- `env.get_video()` 失败不改变已完成 episode 的 metric；
- `_encode_video()` 检查 ffmpeg exit status，非零退出抛出包含有界 stderr 的错误；外层只记录 warning，不把失败路径登记为成功 MP4；
- crash video 同样只用于 diagnosis，不改变 fatal error semantics。

指标与视频 artifact 解耦。

## 12. Evaluation Outputs

### 12.1 Single NFE

```text
<exp>/eval_dexsim/<run-id>/
├── _result.txt
├── result_details.json
└── episode_<seed>.mp4     # 仅启用视频时生成
```

### 12.2 NFE Sweep

```text
<exp>/eval_dexsim/<run-id>/
├── eval_summary.json
├── denoise_timesteps<N1>/
│   ├── _result.txt
│   └── result_details.json
└── denoise_timesteps<N2>/
    ├── _result.txt
    └── result_details.json
```

每次 invocation 分配独立 `<run-id>`（时间戳加随机后缀，排他创建），single-value 和 sweep 都保留历史结果。显式 Python `result_save_dir` 必须为空，结果文件排他写入，不覆盖旧文件。CLI 打印准确 run directory，pipeline summary 指向此 per-run 布局。

启用视频时，对应 NFE 子目录同时保存 MP4；关闭视频不会阻止结果目录与 JSON/TXT 输出。

checkpoint 路径在加载前解析为实际文件，`latest.pt` 后续换指向不会改变已记录的 checkpoint 路径。每个 `result_details.json` 记录实际 checkpoint、raw/EMA choice、denoise steps、reference evaluation seeds、selection exclusion、success metrics 与 per-episode details。Multi-task 的 per-episode details 还带 task identity / task-specific actual seed；顶层 `evaluation_seeds` 是父 runner 使用的 reference seed slice。

结果文件是实验事实；后续分析应优先读取这些输出，而不是根据当前 config 猜测历史 experiment 的 inference recipe。

修改 evaluation 相关代码时至少检查：

```text
[ ] selection candidates 是否使用 paired seeds / positions
[ ] multi-task selection ranking 的 micro denominator 是否保持一致
[ ] best final eval 是否排除 selection reference seeds
[ ] checkpoint 是否经过 strict agent contract validation
[ ] raw / EMA choice 是否显式且可追踪
[ ] Policy RNG 是否按 episode seed 初始化
[ ] observation preprocessing 是否与 validation/deployment contract 一致
[ ] control_action slice 是否遵循 n_obs_steps / n_action_steps
[ ] Policy override 是否仍提供正确的 environment-facing control_action
[ ] NFE 的定义是否与 solver 一致
[ ] multi-task macro / micro denominator 是否正确
[ ] fatal system errors 是否没有被转成 success=False
[ ] video failure 是否不会污染 metrics
```

## 15. Documentation Maintenance Boundary

需要更新本文的变化：

- selection / held-out evaluation protocol；
- seed pairing / resolution semantics；
- checkpoint inference contract；
- EnvRunner episode/failure semantics；
- metric definitions；
- NFE 的跨 solver 公共语义；
- best-demo handoff contract。

不需要更新本文的正常 Policy recipe 变化：

- 当前 decoder/backbone 名称；
- 当前默认 NFE；
- prediction type；
- hidden dim / layer 数；
- batch size / optimizer；
- 当前 Policy 列表。

这些事实回到 resolved experiment config 与对应实现确认。
