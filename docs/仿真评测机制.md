# DexMani_Policy 仿真评测机制

> 本文描述 DexMani_Policy 的**模型选择、仿真评测 protocol、checkpoint restore、seed/metric/failure contract**。
>
> 实验保存的 resolved `config.yaml` 定义模型构造（含 prediction type）、action/window/normalization、输入模态与预处理；普通训练 checkpoint 提供模型/EMA/normalizer 状态。推理不读取 `resume_contract` 的语义。EMA/raw、NFE 是显式 inference 选择。
>
> 系统级训练/评测边界见 [`项目架构.md`](./项目架构.md)。

---

## 1. Evaluation Protocol Overview

DexMani_Policy 将训练、checkpoint selection 和最终性能评测拆成三个阶段：

```text
Training
   │
   ▼
progress milestone checkpoints
   │
   ▼
Checkpoint Selection
   │  paired selection seeds
   │  same inference protocol across candidates
   ▼
selection_result.json（best_ckpt.json 为最近成功选择的别名）
   │
   ▼
Final Evaluation
      held-out seeds
```

核心目的有三个：

1. **训练不拥有 best-model 逻辑**：Trainer 只产出 milestone checkpoints。
2. **candidate checkpoint 公平比较**：selection 阶段对候选 checkpoint 使用相同的 paired seed slice。
3. **避免 selection/evaluation leakage**：`best` 的最终评测排除 selection record 已使用的 seeds。

### 1.1 主要入口

```bash
# 一键：selection → held-out eval（不录视频）
bash scripts/eval/eval_pipeline.sh <policy_name> <task_name> <exp_name>

# 分步
bash scripts/eval/select_best_ckpt.sh <policy_name> <task_name> <exp_name>
bash scripts/eval/eval_best_ckpt.sh <policy_name> <task_name> <exp_name>
bash scripts/eval/record_demo.sh <policy_name> <task_name> <exp_name>
```

运行新 selection 前，确认 saved config 的 manifest 存在，或通过 selector 的 `eval.seed_manifest=...` / pipeline 的 `SEED_MANIFEST` 指定已生成清单。改基础 YAML 不会更新旧实验的 saved config。

实验目录保存推理所需的配置与状态；评测入口读取该快照，不重新 compose 当前仓库的 Policy YAML：

```text
experiments/<policy>/<task>/<exp>/
├── config.yaml
├── checkpoints/
├── best_ckpt.json          # selection 完成后生成
├── eval_ckpt_selector/     # immutable selection result / diagnostic summary / optional videos
├── eval_dexsim/            # final evaluation outputs
└── demo_videos/            # demo recording outputs
```

`<policy>` 可以包含层级路径（例如 DDP config 的 `policy_name`）；不要根据 config 文件名猜实验目录，优先读取实验保存的 config 与实际目录。

## 2. Checkpoint Selection Protocol

`select_best_ckpt.py` 从实验目录发现 progress milestone checkpoints，然后以固定 protocol 比较候选模型。

### 2.1 Candidate Discovery

milestone checkpoint 的命名中包含 progress percentage；selection 只比较可识别的 milestone candidates，而不是训练过程中的任意临时 checkpoint。

训练侧负责产生候选 checkpoint，selection 侧负责决定哪一个作为 best。两者职责分离。

### 2.2 Phase 1 — Paired Initial Evaluation

```text
candidate checkpoint A ─┐
candidate checkpoint B ─┼─ same selection seed slice
candidate checkpoint C ─┘
```

所有 candidate 使用：

- 相同的 episode positions / selection seeds；
- 相同的 EMA 选择；
- 相同的 `inference_steps` / NFE；
- 相同的 environment/evaluation config。

因此 checkpoint comparison 的 denominator 一致。

新 selection 必须有有效 `eval.seed_manifest`，使用完整 selection/tie-break 列表。无效的 `initial_episodes`、`batch_size` 请求参数已删除，旧 CLI 参数会报错；实际数量由清单决定；`max_episodes` 是 selection 加预留 tie-break 的硬上限，不足时在模型加载前报错。快照分别保存请求值与 `effective_episode_counts`。

### 2.3 Exact-Tie Batch

Phase 1 后，只有 top candidates 的 success rate 完全相同时才使用清单预留的完整 tie-break seeds（若非空） 做 tie-break。

如果追加 batch 后仍然 tied，最终 rank key 为：

```text
1. higher success rate
2. lower avg_steps
3. higher global_step
```

`avg_steps` 只在成功 episode 中统计有有效 done-step 的首次物理完成步数，因此它只是 success-rate tie-break，而不是主指标。

### 2.4 Multi-task Selection Metric

selection 内部通过 `collect_episode_details()` 展平 `(task, episode)` units 后保存唯一的 `episode_details` 并据此计算统计。因此 multi-task checkpoint ranking 使用的是**episode-level micro success rate**，不是 `MultiTaskSimRunner` 顶层的 macro success rate。

这意味着 selection 与 final `_result.txt` 的主 success-rate 标量语义保持一致：都按实际完成的 `(task, episode)` units 计数。

### 2.5 合法全零与技术失败

所有 candidate 的 episode 完整、正常且均为零分时，仍按原排名发布选择；全零时最终由较大 `global_step` 决定。不可变结果保存 `selection_all_zero=true`，best 仅引用该结果；`status=success` 表示流程完成，随后继续固定 test。

请求与返回的 `(task, seed)` 多重集必须完全一致，success/steps 字段须有效。空结果、缺失或重复 episode、技术异常及 `failed_tasks` 仍保存失败证据、保留旧 best，并以非零状态退出。正常 timeout/任务未完成属于合法零分。旧记录缺少全零标记只表示未记录。

### 2.6 `best_ckpt.json`

selection record 是 final evaluation / best-demo 的 handoff contract，保存：

- selected checkpoint identity；
- selection performance summary；
- inference choice（raw/EMA、`inference_steps`）；
- selection seed record。

每次 selection 写入 `eval_ckpt_selector/<run-id>/eval_config.yaml` 与 `best_ckpt_selection.json`，包含候选各阶段请求、完成的 episode 明细及实际分母。候选全部完成后，以唯一临时文件和 `os.replace()` 原子发布不可变 selection result，最后原子更新 best 引用。

成功运行保存不可变的 `selection_result.json`，内含候选证据、具体 milestone、inference 设置和选择计划；`best_ckpt.json` 及 `--result-file` 交接文件只存相对引用。eval/demo 的 `--selection-record` 固定解析一次；新结果不依赖诊断 summary 的副本认证，旧 inline 记录仅在 loader 边界解释。具体权重拒绝 latest/symlink。默认 `eval_pipeline.sh` 只启动 selection 与数值 eval，其他 selector 更新 best 不会改变本次已解析的选择。

读取新结果时校验成功状态、已完成候选、具体 checkpoint/global_step/pct 与 inference 设置；诊断 summary 缺失不影响读取。旧 inline 记录在 loader 边界检查其原有证据，无选择身份的记录提示来源未验证。selection 默认关闭录像，`--videos` 显式开启后按 run、候选、阶段和 task 隔离。

## 3. Final Held-out Evaluation

`eval_best_ckpt.py` 可以评测：

- selection 得到的 `best`；
- `latest`；
- milestone tag；
- 显式 checkpoint path。

### 3.1 `best` 的特殊语义

当评测 `best` 时：

1. 只读取一次并严格验证指定的 `--selection-record` 或 `best_ckpt.json`，同时固定当时解析出的具体 checkpoint 路径；
2. 默认复用同一记录中的 inference choice，后续加载使用该具体路径；
3. 从选择记录内嵌 manifest 读取完整 test 清单；仅历史无 manifest 记录沿 legacy 路径排除 selection 已用 seeds；
4. 直接执行每任务实际 seed 列表，检查任务、所用 seed 的可用性、等额预算及 `(task, seed)` 与选择集合无交集；
5. 在加载模型前完成实际计划及 held-out 校验，再运行最终评测。

旧单任务记录的明确 `selection.seeds` 继续可用；旧多任务记录缺少实际 `selection.task_seeds` 时需重新选点。该检查不覆盖其他选点运行或人工调参曾查看的样本，论文比较仍需固定公共协议。

未使用 manifest 时，如果 held-out seed 数少于请求 episodes，则使用全部可用 seeds 并记录实际数量；如果没有任何可用 held-out seed，则失败。显式 manifest 的 test 清单不被 episodes 截短；请求数量不同时提示实际数量，快照分别保存 `episodes` 与 `effective_episodes`。缺失或非法成员直接报错。

### 3.2 Inference Parameter Priority

未指定 `--selection-record` 的普通 `best` 调用中，EMA/NFE 等 inference 参数的优先级是：

```text
explicit CLI
    > explicit OmegaConf/dotlist override
    > best_ckpt.json inference record
    > experiment config
```

显式覆盖 EMA/NFE 仍使用已固定的权重和 selection 证据；即使运行期间发布新 best，也不会混用新权重与旧推理参数。快照记录实际执行的覆盖值。

使用 `--selection-record` 时，EMA/NFE 必须与交接记录一致；冲突的参数或显式 checkpoint 选择直接拒绝。独立 NFE ablation 使用普通 best 或具体 checkpoint 调用，并保存各自结果。

CLI 显式选择非 `best` checkpoint 不依赖 selection record。Python 直接调用 single/sweep 时可传 `resolved_best=(record, concrete_path)`；即使 `ckpt_tag_or_path` 为具体路径，仍保留该记录的 held-out 校验。省略 EMA 或 single 的 NFE 时按 best/config 解析，显式函数参数优先；single 解析出多个 NFE 时应改用 sweep。

### 3.3 Override Boundary

selection/final-eval dotlist 只允许 `eval.*`、`env_runner.*`、`training.seed` 和 `training.device`。其中改变 `n_obs_steps`、`sensor_modalities` 或 RGB resize/crop/uint8 输入语义的字段仍被拒绝。`agent.*`、dataset、normalization 等模型配置不能覆盖；NFE ablation 使用 `--inference-steps`、`eval.inference_steps` 或 `eval.inference_steps_list`。旧推理字段名会报错，不转换为新字段。模型恢复与 runner 输入 recipe 始终重新读取原始 saved config。

有 pinned 协议时，saved config 中的路径只是历史默认值：即使文件移动或内容变化，eval 仍使用记录内嵌清单。本次显式传入 `eval.seed_manifest=...` 则必须与记录 hash 相同；显式 null 同样拒绝。Python single/sweep 通过 `dotlist_overrides` 保留这一显式声明来源。旧无协议记录必须重新选点才能进入新协议。

### 3.4 Demo Handoff

`record_demo.py --ckpt-tag best` 同样一次读取并固定记录与具体权重，复用其中的：

- raw / EMA choice；
- inference steps。

普通 best 调用允许显式 `--ema` / `--no-ema` 与 `--inference-steps` 覆盖；`--selection-record` 则要求它们与记录一致。非 `best` demo 使用 `eval.demo` / shared eval config。

Demo 同样绑定记录内嵌 manifest，在加载模型、覆盖 demo seed 子集前校验完整 runner 池；不接受 dot-list 参数。

Demo 的目的是录制可视化 artifact，不属于 held-out benchmark：默认 seed 选择不会因为 `best` 自动排除 selection seeds；需要复现某个已评测 episode 时应显式传 `--seeds`。

`eval_pipeline.sh` 默认不录视频，也不启动 demo；demo 必须独立显式调用。关闭视频仍保留 RGB Policy 必要相机与离屏渲染。

## 4. Seed and Reproducibility Contract

评测中的“可复现”需要分层理解。

### 4.1 Evaluation Seed Resolution

共享 helper 的基础规则是：

```text
resolved training.seed + fixed offset
```

其中 selection CLI 额外提供 `--seed`，所以 selection 的优先级是：

```text
select_best_ckpt.py --seed
    > resolved training.seed + fixed offset
```

`eval_best_ckpt.py` 当前**没有独立 `--seed` CLI 参数**；final eval 使用 resolved evaluation config 中的 `training.seed + offset`。final-eval dotlist 若显式改写 `training.seed`，也会相应改变 evaluation seed，因为 dotlist 会在 `_setup_eval()` 前合并进 config。该 seed 只影响未指定清单时的池抽样；显式清单不随 shuffle seed 改变。

`record_demo.py` 同样没有独立 `--seed`，但可以用 `--seeds` 直接指定要录制的 episode seeds。

### 4.2 显式论文 seed 清单

`eval.seed_manifest=/absolute/path/seeds.json` 指定 JSON：`pool_id` 提供非空身份标识，`selection`、`tie_break`、`test` 各为 task→有序整数 seed 列表。三个角色覆盖相同 task 集合，selection/test 非空；校验池成员、角色内重复和按 `(task, seed)` 的跨角色交集。同一角色内各任务 episode 数必须相等，直接执行清单中的实际 seeds。

`scripts/eval/make_seed_manifest.py` 读取真实 runner 池并独占创建清单文件；默认 25/5/100 要求至少 130 个配对 seed，不足直接失败。旧清单中的 `runner_pool_sha256` 仅保留为来源证据；执行不再依赖完整池顺序或未使用成员。

selection 保存完整清单、内容 SHA256 和实际 task→seeds。final eval 使用保存的 test 清单，并检查所用任务/seed 的可用性；另传清单必须一致。预留 tie-break seeds 即使没有使用也不会进入 test，训练 seed 改变不会改变这份清单。pipeline 的 `SEED_MANIFEST` 只传 selector；后续阶段传同一 `--selection-record`，不重复传可变路径。

### 4.3 Legacy Final Evaluation

历史无 manifest 记录或无 manifest 的具体 checkpoint 评测，仍将 runner 池保序去重、按 evaluation seed shuffle，排除已知 selection seeds 后取请求数量。该路径用于历史复现；新 selector 不再提供无 manifest 回退。其 test 身份可能随训练 seed 和历史加赛变化，不等价于固定论文协议。

### 4.4 Environment RNG

每个 episode 通过：

```python
env.reset(seed=episode_seed)
```

向 simulator 传入 episode seed。

### 4.5 Policy Sampling RNG

`BaseRunner.run_one_episode()` 在每个 episode 开始时重新设置 Torch CPU/CUDA RNG，使生成式 Policy 的初始噪声与 episode seed 绑定。

因此 checkpoint A 与 checkpoint B 在相同 episode seed 上比较时，Policy RNG 从相同 seed 重新初始化。实际噪声还取决于模型的随机数消费顺序、tensor shape 与 inference steps；不同模型或 NFE 不保证逐次抽样完全相同。

### 4.6 Determinism Boundary

以上保证的是：

- seed slice 可重复；
- environment seed 输入可重复；
- policy RNG 初始化可重复。

**不保证不同运行、不同 GPU/driver/kernel 环境下 bitwise-identical trajectory。** 公共训练/评测环境没有承诺开启全局 deterministic CUDA algorithms，因此文档不应声称“重跑永远得到完全相同结果”。

正确表述是：

> Evaluation protocol is seed-reproducible; bitwise hardware determinism is not guaranteed.

## 5. Multi-task Seed Semantics

`MultiTaskSimRunner.run(task_seeds=...)` 直接消费 `{task: [实际 seeds]}`，按配置任务顺序执行，各任务 episode 数必须相等。例如：

```python
{"task_a": [101, 307], "task_b": [7, 14]}
```

已有显式 manifest 已保存这些实际 IDs，读取后无需 reference/ordinal 映射。生成新清单时保留原 seeded permutation 和最短池预算，将结果一次展开；之后池顺序变化不改变清单中的执行列表。校验所用 seed 可用、角色互斥以及完成的 `(task, seed)` 与请求相符。

Demo 的 `--seeds` 现在显式表示每任务使用的同一组物理 seed 数字，不再按首任务池的位置转换；不指定时仍按各任务池生成固定计划。需要每任务不同的精确列表时，直接调用 `MultiTaskSimRunner.run(task_seeds=...)`。Demo 不作为 held-out 性能证据。

## 6. Checkpoint Restore Contract

三个入口 `select_best_ckpt.py`、`eval_best_ckpt.py` 和 `record_demo.py` 使用 `evaluation/protocol.py` 协调环境和评测控制，再通过 `agents/loader.py` 恢复模型：

```text
load_experiment_config(exp_dir): read original saved config.yaml
      │
      ▼
validate saved model window / action key and evaluation control mode
      │
      ▼
CheckpointStore.load_inference: simple.v3 inference field validation
      │
      ▼
select raw / EMA state
      │
      ▼
instantiate saved config.agent; attach action key / normalization spec
      │
      ▼
repair torch.compile / DDP prefixes
      │
      ▼
agent.load_state_dict(strict=True)
      │
      ▼
validate fitted normalizer → move to device → eval()
```

共享 loader 的 `resolve_best_checkpoint()` 返回 `(record, concrete_path)`。final eval、demo 和 deployment inspection 均传递已解析结果，不在后续加载时再通过可变 best 别名选取权重。

三个入口共用恢复路径。selection 对每个 candidate（含 tie-break）独立恢复，候选共享同一实验的 saved config；推理不读取训练 resume contract 语义。

### 6.1 Agent Compatibility

保存的 config 与 Agent 实现不只定义 parameter shape，还定义 environment-facing action semantics，例如：

- observation/action temporal window（三个字段均为非 bool 正整数，且 `n_obs_steps - 1 + n_action_steps <= horizon`；与训练共用 validator）；
- action dimension / action key；
- control-action dimension；
- Policy-specific hand/TCP dimensions；
- auxiliary-action semantics。

因此：

> 一个 checkpoint 的 tensors 即使能够“看起来匹配”，也不代表它在语义上可以用于当前 Agent。

### 6.2 Raw vs EMA

- `use_ema=True` 时 checkpoint 必须真的包含 EMA state；缺失时直接失败。
- `use_ema=False` 才显式使用 raw model state。

不做 silent fallback。

### 6.3 Prefix Repair

评测通过 `training/checkpoint.py::fix_state_dict` 处理训练包装引入的 state-dict prefix，例如：

- `torch.compile` 的 `_orig_mod.`；
- DDP 的 `module.`。

最终始终用 `strict=True` 加载到单卡 inference Agent。

### 6.4 Normalizer Restore

Normalization mode 由 saved config 解析，拟合参数来自选中的 raw/EMA state。校验覆盖字段和 fitted state 的完整性、有限性、非零 scale。推理不读取训练数据重新拟合统计量。

DQ-RISE 构造时不读取训练时的 external `codebook_path`；strict state load 恢复 persistent codebook，并验证结构和 hand normalizer 与 Policy 一致。完整 checkpoint 不依赖原 NPZ 文件。

## 7. Observation Runtime

### 7.1 Temporal Ring Buffer

`BaseRunner` 为 configured sensor modalities 维护长度为 `n_obs_steps` 的 temporal buffer。

```text
env.reset / env.step
      │
      ▼
update_obs
      │
      ▼
ring buffer
      │
      ▼
get_stacked_obs
      │
      ▼
(T=n_obs_steps, ...)
      │
      ▼
get_obs_batch
      │
      ▼
(B=1, T=n_obs_steps, ...)
```

冷启动阶段如果有效观测少于 `n_obs_steps`，使用 episode 第一帧在序列头部 padding，使最新真实观测保持在时间窗口尾部。

buffer 满后通过时间索引重新排列为 chronological order。该读取使用 advanced/fancy indexing，不能视为零拷贝接口；优化重点是避免每一步重新分配写入 storage，而不是承诺读取零 allocation。

### 7.2 Modalities

`update_obs()` 只保存 `sensor_modalities` 中声明的字段。

典型语义：

- `joint_state`：进入 temporal buffer，并由 Policy normalizer 处理；
- `point_cloud`：进入 temporal buffer；normalization mode 由 saved config 定义，非 identity 的 fitted state 随 Agent checkpoint 恢复；
- `rgb`：当 config 将其列入 `sensor_modalities` 时进入 buffer，随后执行与 validation 对齐的确定性 spatial preprocessing；
- `task_text`：通常由 `TaskTextSimRunner` 在 inference boundary 注入，而不是依赖环境 ring buffer。

不要把“RGB”泛化成非传感器模态，也不要把 point-cloud normalization 误写成只由 encoder 内部完成。

### 7.3 RGB Path

Evaluation 和 Real runtime 都复用 `datasets/preprocessing.py` 的 deterministic validation preprocessing，参数来自 saved dataset config：

```text
raw [..., H, W, 3] uint8 RGB
    │
    ├── no resize: keep HWC uint8 (center crop must be absent)
    │
    └── resize: convert to CHW → bilinear resize → optional center crop
                 ├── keep_uint8 + no training color aug: uint8 spatial path
                 ├── keep_uint8 + training color aug: float32 spatial → final uint8
                 └── otherwise: float32 in [0, 1]
    │
    ▼
Agent-owned ImageProcessor → vision encoder
```

`resize_hw` 来自 `rgb_preprocess_size`，`center_crop_hw` 来自 `rgb_random_crop_size`；`keep_uint8` 直接对应 `rgb_keep_uint8`（缺省 false）。保存的训练 recipe 含 `rgb_color_aug` 时，内部派生 `float_spatial_before_uint8=True`：先转 float32 /255 做 spatial preprocessing，最终按 `mul(255).round().clamp(0,255)` 量化回 uint8，避免切换成 uint8 插值。未配置 resize 时保留原始 HWC uint8，与 keep_uint8 设置无关；crop 单独存在会失败。

训练时的 random crop / color augmentation 不在 evaluation 中启用。

## 8. Agent Inference and Action Chunk Semantics

公共 inference path：

```text
obs_dict
   │
   ▼
Agent.predict_action
   │
   ├── validate observation contract
   ├── preprocess / normalize
   ├── ObsEncoder → condition
   └── predict_action_from_cond
           │
           ├── generative decoder sampling
           ├── action unnormalize / representation decode
           └── control chunk slicing
```

### 8.1 Default Action Slice

`BaseAgent` 的默认时间对齐规则：

```python
start = n_obs_steps - 1
control_action = pred[:, start : start + n_action_steps]
tail = pred[:, start + n_action_steps :]
```

因此诸如 `pred[:, 1:9]` 只是特定 `(n_obs_steps, n_action_steps)` recipe 的实例，不是架构 contract。

Policy 可以 override `predict_action_from_cond()`；不要假设所有 override 都返回 `tail`。

### 8.2 Model Output vs Control Action

某些 Policy 会预测 auxiliary action dimensions。此时：

```text
model action_dim
    ≠
environment-facing control_action_dim
```

Agent 在 inference boundary 截取真正传入 `env.step()` 的控制维度。

### 8.3 Internal Action Representation

公共 rollout 只要求 Agent 提供可执行的 `control_action`。通常还会返回完整 `pred_action`，但其他诊断字段（例如 `tail`、code index 等）可以是 Policy-specific。

因此 Policy 内部可以使用不同表示，例如 structural/action-dimension tokens 或 reduced/quantized hand representation，只要在 Agent boundary 恢复正确的 environment-facing control semantics。

## 9. Inference Algorithm Families

Evaluation 层通过 Agent 将运行时 `inference_steps` 传给 Action Decoder，覆盖本次推理步数；其采样算法由 decoder/solver 决定。

### 9.1 Diffusion / DDIM

```text
x ~ N(0, I)
   │
   ▼
DDIM timestep schedule
   │
   ├── model(x_t, t, condition)
   └── scheduler.step
   │
   ▼
predicted action sequence
```

model output 的语义由 `prediction_type` 决定，例如 clean sample、noise 或 velocity prediction。

training timesteps 与默认 decoder 构造参数来自 saved config；本次 inference steps 由显式 CLI、selection record 与 evaluation config 按已有优先级决定，不在本文固定。

### 9.2 Flow Matching / Euler ODE

典型 rectified path：

```text
x_t = (1 - t) x_noise + t x_data
v*  = x_data - x_noise
```

训练学习 velocity field；推理从 Gaussian noise 出发，通过 ODE integration：

```text
x_{t+dt} = x_t + dt · vθ(x_t, t | condition)
```

Flow Matching 是 training objective；它本身不意味着 one-step inference。

### 9.3 Consistency-enhanced Flow

某些 decoder 会在普通 flow velocity regression 之外加入 teacher/consistency target，并让模型显式接收 target step / step-size conditioning。

当前 [ManiFlow decoder](../dexmani_policy/agents/action_decoders/consistency_flow.py)
用构造参数 `denoise_timesteps` 设置 consistency 训练离散网格，用 `num_inference_steps`
设置默认 Euler 推理 NFE。评测的 `inference_steps` 通过运行时参数覆盖推理 NFE，
不会修改训练 sampler 或 consistency denominator。训练网格、默认 NFE 与运行时覆盖使用不同参数名。

这类模型在 inference 时可能使用训练过的非零 step-size condition。若训练只覆盖 instantaneous-flow condition，而 inference 使用不同 condition，会产生 conditional distribution shift；是否存在这种路径必须从当前 decoder 与 config 验证。

### 9.4 NFE Sweep Fairness

做 NFE sweep 时，不同 NFE 使用同一个 **实际 task→seeds 计划**。对于 `best`，该 slice 已排除 selection seeds，因此属于 held-out final-eval seeds；对于 `latest`、milestone 或未附带 `resolved_best` 的显式 path，则只是同一评测 seed slice，不应称为 selection-held-out。

这样 success-rate 差异主要反映 inference compute budget，而不是 environment-instance sampling 差异。

## 10. Episode Semantics and Metrics

### 10.1 `success_condition` vs `success`

单 episode 区分两个信号：

```text
success_condition
    = 首次满足任务物理目标的 raw condition

success
    = 环境最终认可的成功结果，可包含 hold / grace 条件
```

`task_done_step` 在首次 truthy `success_condition` 时读取 `env.action_cnt`；如果环境没有提供该 contract，则 done step 可以是 `None`。

因此：

- success rate 使用最终 `success`；
- successful completion speed 使用有值的 `task_done_step`。

### 10.2 Single-task Metrics

```text
success_rate
    = successful episodes / completed valid episodes

avg_steps
    = mean(task_done_step) over successful episodes with a valid done step

avg_steps_all
    = mean(total episode steps) over episode details that have total_steps
```

失败 episode 参与 `success_rate` 和通常的 `avg_steps_all`，但不参与 success-only `avg_steps`。

### 10.3 Multi-task Metrics

Multi-task runner 同时计算：

```text
per-task success rate

macro_success_rate
    = mean(per-task success rate)

micro_success_rate
    = total successful (task, episode) units
      / total completed (task, episode) units
```

macro 衡量 task-level 平均表现；micro 按实际 episode units 加权。两者不应混用。

最终 `eval_best_ckpt.py` 会重新从 episode details 计算 micro statistics：

- `_result.txt` 写入 **micro success rate**；
- `result_details.json` 同时保存 `success_rate`（micro）和 `macro_success_rate`。

因此读取 multi-task 历史结果时，不要把 `_result.txt` 的单值误解为 macro average。

## 11. Failure Semantics

评测严格区分“模型正常执行但任务失败”和“评测系统本身出错”。

### 11.1 Genuine Task Failure

```text
episode executes normally
+ info["success"] == False
→ valid result: success=False
```

这是正常 benchmark outcome。

### 11.2 Fatal Episode Failure

model forward、environment step、OOM、runtime contract 等异常在单任务 runner 中被分类并转换为 `EvalEpisodeError`，随后终止当前评测，而不是记成普通 0% episode 继续。

这避免 infrastructure/model errors 被统计成 task failure。

### 11.3 Multi-task Failure

`MultiTaskSimRunner` 对 child `EvalEpisodeError` 直接向上抛出。某些发生在 task orchestration boundary 的普通 runtime/config errors 可以先记录为 failed task，但最终会拒绝报告 reduced aggregate result，并以异常结束。

因此不能把“缺失一个 task 后剩余任务的 macro average”当成有效 benchmark。

### 11.4 Video Failures

视频是 best-effort artifact：

- `env.get_video()` 失败不改变已完成 episode 的 metric；
- `_encode_video()` 检查 ffmpeg exit status，非零退出抛出包含有界 stderr 的错误；外层只记录 warning，不把失败路径登记为成功 MP4；
- crash video 同样只用于 diagnosis，不改变 fatal error semantics。

指标与视频 artifact 解耦。

## 12. Evaluation Outputs

### 12.1 Single NFE

```text
<exp>/eval_dexsim/<run-id>/
├── eval_config.yaml
├── _result.txt
├── result_details.json
└── episode_<seed>.mp4     # 仅启用视频时生成
```

### 12.2 NFE Sweep

```text
<exp>/eval_dexsim/<run-id>/
├── eval_config.yaml
├── eval_summary.json
├── inference_steps<N1>/
│   ├── _result.txt
│   └── result_details.json
└── inference_steps<N2>/
    ├── _result.txt
    └── result_details.json
```

每次 invocation 分配独立 `<run-id>`（时间戳加随机后缀，排他创建），single-value 和 sweep 都保留历史结果。显式 Python `result_save_dir` 必须为空，结果文件在同目录临时文件写完整后排他发布，不覆盖旧文件。CLI 打印准确 run directory，pipeline summary 指向此 per-run 布局。

启用视频时，对应 NFE 子目录同时保存 MP4；关闭视频不会阻止结果目录与 JSON/TXT 输出。

`eval_config.yaml` 保存最终解析后的 CLI/配置请求、展开后的环境参数、历史模型配置来源、runner 实际模型输入及代码版本。使用 best 时，`request` 还保存固定记录的 `selection_id`、`selection_summary` 和 `selection` 证据，以及实际 checkpoint、EMA/NFE、shuffle seed 和 task/seed；历史记录缺少的身份字段为 null。sweep 父快照记录完整 NFE 列表，子结果记录实际 NFE。代码 dirty 标志不等于源码归档；版本不可取得时记录 unknown。

结果保留每任务成功数与实际分母，增加 95% Wilson 区间；n=0 返回 null，不为 macro 套二项区间。该区间描述 episode 抽样不确定性，不替代多个训练 seed 的方差，也不参与排名。

checkpoint 路径在加载前解析为实际文件，`latest.pt` 后续换指向不会改变已记录的 checkpoint 路径。每个 `result_details.json` 记录实际 checkpoint、raw/EMA choice、`inference_steps`、实际 task→seeds 计划、selection exclusion、success metrics 与 per-episode details。Multi-task 的 per-episode details 还带 task identity / task-specific actual seed；顶层 `evaluation_seeds` 保存每任务的实际 seed 列表。

结果文件是实验事实；后续分析应优先读取这些输出，而不是根据当前 config 猜测历史 experiment 的 inference recipe。

### 12.3 Demo

`record_demo.py` 在 `demo_videos/<run-id>/` 保存 `eval_config.yaml`、`result_details.json` 和录像；显式 `--output-dir` 更换父目录，每次调用仍创建独立 run。NFE sweep 的结果和录像放入 `inference_steps<N>/`，多任务录像再按任务分目录。结果记录具体 checkpoint、step、raw/EMA、NFE 和 episode 明细，并标记 `heldout_from_selection=false`。

demo 只验证实际请求的 task→seeds；空列表、重复或不可用 seed 均拒绝。不读取未使用的 test role 或外部 manifest。`--selection-record` 仍验证选择记录并锁定 checkpoint/EMA/NFE，不能用 demo 绕过交接冲突检查。快照的 `seed_manifest` 为 null，旧配置路径与 selection 内嵌协议仅作来源记录；正式 held-out 入口仍解析和验证完整协议。保存快照本身不重新绑定或打开清单。

selection、held-out eval 和 demo 在共享结果边界检查 episode：success 仅接受 bool/np.bool_，seed 为匹配实际计划的非 bool 整数，steps 为非负整数或 None。缺失、重复、额外 episode、错误任务、异常记录或 failed_tasks 均报错；附加 metadata 可以保留。统计和排名消费已通过校验的结果，字符串 `"False"` 不会被当作成功。

## 13. Evaluation Review Checklist

修改 evaluation 相关代码时至少检查：

```text
[ ] selection candidates 是否使用 paired seeds / positions
[ ] multi-task selection ranking 的 micro denominator 是否保持一致
[ ] best final eval 是否排除 selection 实际 task/seed
[ ] 是否使用原始 saved config 构造并 strict restore checkpoint / normalizer
[ ] raw / EMA choice 是否显式且可追踪
[ ] Policy RNG 是否按 episode seed 初始化
[ ] observation preprocessing 是否与 validation/deployment contract 一致
[ ] control_action slice 是否遵循 n_obs_steps / n_action_steps
[ ] Policy override 是否仍提供正确的 environment-facing control_action
[ ] NFE 的定义是否与 solver 一致
[ ] multi-task macro / micro denominator 是否正确
[ ] fatal system errors 是否没有被转成 success=False
[ ] video failure 是否不会污染 metrics
```

## 15. Documentation Maintenance Boundary

需要更新本文的变化：

- selection / held-out evaluation protocol；
- seed pairing / resolution semantics；
- checkpoint inference contract；
- EnvRunner episode/failure semantics；
- metric definitions；
- NFE 的跨 solver 公共语义；
- best-demo handoff contract。

不需要更新本文的正常 Policy recipe 变化：

- 当前 decoder/backbone 名称；
- 当前默认 NFE；
- prediction type；
- hidden dim / layer 数；
- batch size / optimizer；
- 当前 Policy 列表。

这些事实回到 resolved experiment config 与对应实现确认。
