# DexMani_Policy 训练流程修正与本地验证方案

> 目标：指导 Codex 对训练流程做**最小、可验证、低维护成本**的修正，并在本地 `policy` Conda 环境中完成针对性实验，将真实执行结果回填到本文档。
>
> 本文只讨论 training/data/optimizer/resume/logging 流程，不讨论模型结构、Observation Representation、Action Decoder、Diffusion/Flow objective 等算法结构。

## 1. 项目定位与执行原则

DexMani_Policy 是个人具身智能研究代码库，不是通用训练平台，也不是生产训练基础设施。本轮修改必须遵循以下原则：

1. **只修已确认的问题，不为假设风险预建复杂机制。**
2. **不引入新的框架依赖。** 不迁移到 Accelerate、FSDP、DeepSpeed 等。
3. **不改变默认训练算法语义。** `obs_lr > 0` 时，现有优化器、scheduler、EMA、DDP、gradient accumulation 行为应保持不变。
4. **不重构 Trainer 状态机。** 当前 optimizer-step clock、EMA/scheduler boundary、DDP `no_sync`、NaN protection、resume cursor 都保留。
5. **验证成本从低到高。** 先静态检查/targeted script，再 full smoke；只有确有必要时才做短训练。
6. **实验失败时先记录，不通过扩大重构“解决”。** 若实验暴露新的独立问题，记录为 follow-up，不顺带加入本任务。
7. `robot_data/`、`experiments/`、checkpoint、视频、W&B 日志等生成物不得提交。临时实验输出优先放 `/tmp/`。
8. 修改前必须读取当前 `AGENTS.md`，并以当前 HEAD 代码为 source of truth；本文给出的文件与逻辑基于编写时 HEAD `c840beb4f8aa04a22e90ddb1007ea5c264481b36`，若代码已变化，先重新 fact-check 再实施，禁止机械套 patch。

以下事项经过与参考项目对比后，不应在本轮工程化：

- 不把 normalizer 改为 train-subset-only。官方 Diffusion Policy 在存在 `train_mask/max_train_episodes` 的数据集里也常直接用完整 replay buffer 统计；只有正式做 data-efficiency / held-out methodology 时再单独处理。
- 不自动缩放 DDP step/LR/warmup。当前 `4 × 48 = 192` 与单卡 `64` 是不同 recipe，只需在 controlled comparison 时人工对齐 global batch。
- 不重写 partial gradient accumulation。当前 Trainer 已按实际 `group_size` 缩放 loss，不是 correctness bug。
- 不实现 stateless augmentation、worker RNG checkpoint、prefetch queue restore。
- 不做 dataset fingerprint / Git/environment manifest 系统。
- 不做 lazy Zarr；当前 in-memory replay 与官方 Diffusion Policy 的推荐路径一致，RAM 真正成为瓶颈时再处理。
- 不拆 weights/state/milestone 三套 checkpoint；当前 20/40/60/80/100% 与仓库离线 best-checkpoint 评测工作流一致。
- 不增加 FSDP/DeepSpeed/Accelerate。
- 不增加复杂 profiler、CPU/GPU memory telemetry、H2D breakdown。
- 不为了曲线平滑增加 rolling loss framework；W&B 可自行 smooth。
- 不新增 `init_from`，除非当前研究任务已经需要 weights-only warm start。

## 3. Task A：修复 `obs_lr=0` 的真实 freeze 语义

### 3.1 当前事实

`dexmani_policy/training/build_utils.py::validate_config()` 明确允许：

```text
optimizer.obs_lr >= 0
0 means freeze
```

但 `dexmani_policy/agents/core/base.py::configure_optimizer()` 当前只是把 observation parameter group 的 LR 设成 `0`。因此 observation encoder 仍然：

- `requires_grad=True`；
- 参与 autograd；
- 可能产生 `.grad`；
- 参与 `clip_grad_norm_(self.raw_model.parameters(), ...)`；
- 被加入 AdamW parameter groups，并可能分配 optimizer moments；
- 只是最终 parameter update 因 `lr=0` 为零。

这与“freeze”语义不一致，而且 observation gradient 仍可能影响全模型 global grad clipping。

### 3.2 目标语义

当且仅当显式设置：

```yaml
optimizer:
  obs_lr: 0
```

应得到 **parameter freeze**：

```text
obs_encoder parameters: requires_grad=False
obs_encoder parameters: 不进入 optimizer
obs_encoder parameters: backward 后 grad is None
action/policy parameters: 保持原有 trainable 状态并正常更新
```

本轮只定义“参数冻结”，**不要额外改变 module train/eval mode**。即不要为了 freeze 自动 `obs_encoder.eval()`，避免顺带改变 Dropout/Norm 等训练语义。

当 `obs_lr is None` 时仍回退到 `lr`；当 `obs_lr > 0` 时行为必须与当前实现一致。

### 3.3 最小实现建议

优先只改：

```text
dexmani_policy/agents/core/base.py
```

在 `BaseAgent.configure_optimizer()` 中，在构造 parameter groups **之前**处理：

```python
obs_lr = obs_lr if obs_lr is not None else lr
obs_wd = obs_weight_decay if obs_weight_decay is not None else weight_decay

if obs_lr == 0:
    self.obs_encoder.requires_grad_(False)

# 然后继续现有 get_optim_param_groups / AdamW 构造
```

这样现有 `get_optim_group_with_no_decay()` 会自动跳过 `requires_grad=False` 的 observation 参数，`_check_params_in_optimizer()` 也不会把它们判为漏参。

不要引入新的 freeze manager、parameter registry 或 config 字段。

### 3.4 必须检查的 blast radius

Codex 修改前应搜索：

```bash
grep -R "configure_optimizer(" -n dexmani_policy
grep -R "obs_lr" -n dexmani_policy/configs dexmani_policy
```

确认是否存在任何调用场景会在同一个 model 实例上重复调用 `configure_optimizer()` 并期待从 `obs_lr=0` 再恢复成 `obs_lr>0`。若不存在，则保持上述最小实现；不要为理论上的重复调用增加状态恢复机制。

### 3.5 本地实验 A：真实模型 freeze A/B

使用真实 `dp` config，不新增永久测试文件。建议写 `/tmp/check_obs_freeze.py` 临时脚本，使用：

```text
load_config("dp")
→ build_dataset_and_normalizer
→ build_train_loader
→ build_model_and_ema
→ configure_optimizer
→ one batch forward/backward/step
```

#### A1：`obs_lr=0`

运行时覆盖：

```python
cfg.optimizer.obs_lr = 0.0
cfg.training.use_compile = False
cfg.training.use_ema = False
```

必须记录并断言：

1. `sum(p.numel() for p in model.obs_encoder.parameters() if p.requires_grad) == 0`
2. optimizer 中不存在任何 `obs_encoder` parameter id。
3. backward 后 observation parameters 的 `grad is None`。
4. 至少一个 action decoder trainable parameter 有非空有限 gradient。
5. `optimizer.step()` 后 observation encoder state 不变。
6. `optimizer.step()` 后至少一个 action decoder parameter 发生变化。
7. loss finite。

建议对参数变化只抽样 1~3 个明确的 action trainable tensor，不要复制整个大模型做昂贵比较。

#### A2：`obs_lr>0` regression

使用 config 原始 `obs_lr`，重复构造 model/optimizer，确认：

1. observation encoder 仍存在 trainable params；
2. optimizer 包含 observation trainable params；
3. backward 后至少一个 observation trainable parameter 获得 finite gradient；
4. full smoke 不受影响。

#### A 的验收标准

- A1 全部满足：PASS。
- A2 保持当前行为：PASS。
- 如果 A1 中 observation grad 仍出现：FAIL，先定位依赖，不继续其它重构。

## 4. Task B：校正 resume reproducibility 的边界描述

### 4.1 当前事实

当前 checkpoint 已保存：

- Python RNG；
- NumPy RNG；
- Torch CPU RNG；
- CUDA RNG；
- per-rank RNG list；
- epoch；
- `next_micro_step`；
- deterministic distributed sampler ordering/cursor；
- model / EMA / optimizer / scheduler / EMA counter。

这足以恢复训练主进程随机状态和 sample ordering。

但实际 augmentation 发生在 DataLoader worker 内，包括例如：

- `np.random.random()` 的 state/point augmentation；
- `torch.randint()` 的 random crop；
- torchvision random color augmentation；
- persistent worker 自身 RNG 进度。

checkpoint 没有保存 worker RNG state 与 prefetch queue。因此“resume 后完全复现 uninterrupted run 的 augmentation stream”不能由当前实现保证。

### 4.2 本轮修改

只修改：

```text
dexmani_policy/common/pytorch_util.py
```

重点修正 `get_rng_state()` docstring。建议语义：

```text
Capture the main-process Python/NumPy/Torch/CUDA RNG state for checkpoint resume.
Together with the resumable sampler this restores process RNG and sample ordering.
Randomness consumed inside DataLoader workers (e.g. stochastic augmentation with
persistent workers/prefetching) is not guaranteed to be bit-exact across resume.
```

`set_rng_state()` 可以保留，也可同步补一句“main-process RNG”。

不要修改 checkpoint schema，不实现 worker RNG 保存，不改 DataLoader。

### 4.3 本地实验 B：验证 sample-order 与 augmentation 的边界

该实验是为了验证文档边界，而不是要求 bit-exact。

建议临时脚本 `/tmp/check_resume_augmentation.py`，使用真实 `dp` dataset，保持 production-like：

```text
num_workers >= 2
persistent_workers = true
shuffle = true
state noise 保持开启
RGB random crop/color aug 保持开启
```

实验逻辑：

1. `set_seed(seed)`，构造 dataset + loader A。
2. sampler 设置 `epoch=0, next_micro_step=0`。
3. 消费 K 个 batch（如 K=3）。
4. 在第 K 个 batch 后记录主进程 `get_rng_state()`，这模拟 checkpoint 时保存的 process RNG。
5. 从原 loader A 再取一个 batch，记为 `continued_batch`。
6. 销毁 iterator/loader A（必要时显式删除并让 workers 退出）。
7. 重新 `set_seed(seed)` 并构造同配置 dataset + loader B。
8. sampler B 设置 `epoch=0, next_micro_step=K`。
9. 恢复第 4 步保存的主进程 RNG。
10. 从 loader B 取首个 batch，记为 `resumed_batch`。

比较：

```text
action_equal
joint_state_equal / max_abs_diff
rgb_equal / max_abs_diff
```

预期解释：

- **关键要求：`action_equal == True`。** action 未被随机 augmentation 修改，因此它可作为 sample ordering/cursor 的代理。若不相等，说明可能存在真正的 sampler resume 问题，应升级为 MAJOR 并停止只改文档的方案。
- stochastic observation 是否相同必须以真实实验为准。根据当前实现，预计至少 `joint_state` 或 `rgb` 会出现差异；若确实不同，即验证“worker augmentation 非 bit-exact”的边界。
- 如果 observation 意外完全相同，先确认 augmentation 实际触发、workers>0、persistent_workers 生效，再重复 2~3 次；仍相同则如实记录，不强行制造差异。

### 4.4 B 的验收标准

- sample ordering 可恢复：PASS。
- 文档不再宣称 worker augmentation bit-exact：PASS。
- 不要求 augmentation exact；不因此增加任何工程机制。

## 5. Task C：增加最小 throughput telemetry

### 5.1 目标

增加两个稳定、低成本指标：

```text
train/step_time
train/samples_per_sec
```

目的仅用于个人研究中比较：

- `torch.compile` on/off；
- 不同 batch size；
- single GPU / DDP；
- 不同 policy/encoder 的训练吞吐。

不要扩展成 profiler。

### 5.2 指标定义

建议使用 **log window wall-clock average**，不在每个 CUDA op 前后 `synchronize()`，避免人为增加同步开销。

在两个 logging event 之间统计：

```text
elapsed_wall_time
optimizer_updates
actual_samples_consumed
```

定义：

```text
train/step_time = elapsed_wall_time / optimizer_updates
train/samples_per_sec = actual_samples_consumed / elapsed_wall_time
```

其中 `actual_samples_consumed` 应尽量用真实 batch size 计数，而不是硬编码 config：

```text
每个 micro-batch：local_samples += batch["action"].shape[0]
optimizer boundary：global_samples += local_group_samples × world_size
```

当前 DDP `DistributedSampler` 各 rank local batch 规模一致；默认 `drop_last=true` 时该值与 nominal effective batch 一致。这样即使未来 gradient accumulation/最后一个 batch 改变，也不需要额外公式。

### 5.3 实现位置

只改：

```text
dexmani_policy/training/trainer.py
```

建议最小状态：

```python
self._perf_window_start_time
self._perf_window_updates
self._perf_window_samples
```

在 `train()` 真正开始 loop 后初始化。

每个 micro-batch 累加 local sample count；每个 accumulation boundary：

- `updates += 1`
- `samples += local_group_samples * world_size`
- group sample count 清零。

在现有 `global_step % log_interval_steps == 0` 分支中计算两个指标并加入 `step_metrics`，随后 reset performance window。

不要增加新的 config。不要修改 existing loss/lr/grad logging key。

### 5.4 关于计时语义

允许该 wall-clock 指标包含 DataLoader wait 和正常训练 loop overhead，因为它回答的是“从研究者角度每秒实际处理多少训练样本”。

不要为了排除 milestone checkpoint、W&B、DataLoader 等额外重写 loop。记录结果时说明这是 **end-to-end log-window throughput**，不是纯 GPU kernel throughput。

### 5.5 本地实验 C：telemetry sanity check

优先用临时 harness，避免为了 5 个 milestone 保存大 checkpoint。

推荐方案：

1. 用真实 `dp` config 构造 dataset/model/optimizer/scheduler。
2. `use_compile=False`、`use_ema=False`，降低第一次验证成本。
3. 构造 `Trainer` 时使用一个只收集 `log()` 的临时 `CaptureWorkspace`，并在测试脚本里将 `_check_milestone` 临时 monkeypatch 为 no-op；**不要把 monkeypatch 提交进仓库**。
4. 跑 3~5 个 optimizer steps，`log_interval_steps=1` 或 2。
5. 从 CaptureWorkspace 收集 telemetry。

必须检查：

```text
step_time > 0
samples_per_sec > 0
isfinite(step_time)
isfinite(samples_per_sec)
```

并检查近似关系：

```text
samples_per_sec × step_time ≈ samples_per_optimizer_update
```

对 `grad_accum=1`、固定 full batch，该误差应非常小；wall-clock window/边界实现若导致较大偏差，应检查 sample counter/reset 位置。

如果本地有多卡并且已经方便启动 DDP，可额外做一次 2-GPU sanity check；**不是本轮必需验收项**。

## 6. Task D：检查 DINO LoRA + AdamW 的 optimizer state dtype（只检查）

### 6.1 为什么检查

当前 DINO 通过：

```python
torch_dtype=torch.bfloat16
```

加载，并在 LoRA 注入后显式把 `lora_` 参数 cast 到 backbone dtype。因此 trainable LoRA parameter 很可能是 bf16。

PyTorch AdamW 的 `exp_avg` / `exp_avg_sq` state dtype 需要实际运行后确认。该行为可能完全可用，因此本轮**禁止仅凭代码阅读就改成 FP32 master weights**。

### 6.2 本地实验 D

用原始 `dp` config：

```python
cfg.training.use_compile = False
cfg.training.use_ema = False
```

完成：

```text
build model
build optimizer
one real batch forward
backward
optimizer.step()
```

然后找到一个：

```text
name contains "lora_" and parameter.requires_grad
```

记录：

| field | value |
|---|---|
| parameter name | ... |
| parameter dtype | ... |
| grad dtype | ... |
| optimizer `exp_avg` dtype | ... |
| optimizer `exp_avg_sq` dtype | ... |
| parameter finite | true/false |
| grad finite | true/false |
| optimizer state finite | true/false |

同时记录 action decoder 中一个典型 FP32/BF16 trainable parameter 的同类信息用于对照。

### 6.3 决策规则

- 若 LoRA param/state 为 bf16，但 one-step 与现有正常训练均 finite：**记录事实，不修改代码**。
- 若 state 为 FP32：记录即可，无需修改。
- 若可稳定复现 non-finite / 明显数值异常：标记 `FOLLOW-UP REQUIRED`，停止本轮，不把 dtype 重构混入本任务。

本实验的目的只是回答“实际 dtype 是什么”，不是证明几十万步的最终收敛质量。

## 9. Stop Conditions

出现以下情况时，不继续扩大修改：

1. **Experiment B 中 `continued_batch["action"] != resumed_batch["action"]`**：这可能是真正的 sampler/cursor resume bug，标记 MAJOR，单独调查。
2. **Experiment A 的 `obs_lr=0` 仍产生 obs gradient 或 optimizer 包含 obs param**：当前 freeze 修复失败，先修根因。
3. **Experiment D 出现 non-finite optimizer state**：记录并开 follow-up，不在本任务中重构 mixed precision。
4. full smoke 暴露与本 diff 无关的已有环境问题：记录 NOT VERIFIED/环境限制，不修无关代码。
5. 为完成任一检查需要引入新 dependency、FSDP、Accelerate、复杂 test framework：停止，改用临时脚本或更小验证。

## 10. 最终验收条件

本轮任务只有在以下条件满足时才可标记完成：

- [ ] `obs_lr=0` 真实冻结 observation parameters，且不进入 optimizer、不产生 grad。
- [ ] 原始 `obs_lr>0` 路径无 regression。
